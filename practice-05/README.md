## Эксперимент с очередями выполнения

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A, B, C, D, E, F | A, B, C — синхронный код (B печатается внутри `demonstrateAwait` до первого `await`). Затем микрозадачи в порядке постановки: D (`.then` зарегистрирован раньше), E (продолжение после `await null`). F — задача таймера, выполняется после опустошения очереди микрозадач |
| Фактический результат | A, B, C, D, E, F | Совпало с прогнозом |
| Прогноз с собственным `Promise.resolve().then(G)` (добавлен после вызова `demonstrateAwait()`) | A, B, C, D, E, G, F | G ставится в очередь микрозадач третьим — после D и E, но раньше таймера |
| Фактический результат | A, B, C, D, E, G, F | Совпало |

- **Синхронный код:** A, B, C. `async`-функция выполняется синхронно до первого `await`.
- **Микрозадачи:** D (обработчик `.then`), E (продолжение после `await`), G (собственный обработчик). Они выполняются строго в порядке постановки, когда стек вызовов пуст.
- **Таймер с задержкой 0** означает «не раньше чем через 0 мс в следующей задаче», а не «немедленно»: сначала завершается текущий скрипт и опустошается вся очередь микрозадач.
- **Если удалить один из обработчиков Promise**, исчезнет только его строка; относительный порядок остальных не изменится — F всё равно последняя.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный API (не изменялся): маршруты задач и категорий, фильтры, ошибки, CORS, отладочные маршруты. |
| `src/api-client.js` | Транспорт: `buildUrl`, `createApiClient` → `requestJson`. URL, `GET` + `Accept`, тайм-аут и отмена, проверка статуса и `Content-Type`, разбор JSON, единый `ApiError`. О задачах не знает. |
| `src/task-api.js` | Предметная область: маршруты `/tasks`, `/tasks/:id`, `/categories`, проверка фильтров до запроса, проверка схемы ответа после, `loadInitialData` через `Promise.all`. |
| `src/variant.js` | Только данные варианта: `variantNumber = 1`, `variantFilters = { completed: false }`. |
| `src/main.js` | Консольный сценарий: создаёт клиент, загружает данные, печатает таблицу и контрольную ошибку 404. |

- **`fetchFn` передаётся в `createApiClient`**, чтобы модульные проверки подставляли поддельный `fetch`: возвращать подготовленные `Response`, моделировать сетевой отказ и медленный ответ — без сети и без запущенного сервера.
- **HTTP-ошибки проверяются отдельно от сетевых**: `fetch` обёрнут в собственный `try`, а `response.ok` проверяется уже после него. Иначе `ApiError` с `kind: "http"`, созданный при обработке ответа, попал бы в общий `catch` и превратился бы в `network`, потеряв статус и код API.
- **JSON проверяется по контракту**, потому что синтаксически верный `{"data":"не массив"}` или задача с `id: "4"` сломают вызывающий код позже и в неожиданном месте. `task-api.js` превращает такое расхождение в `invalid-response` сразу на границе.

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | `new URL(baseUrl)`; только `http:`/`https:`; запрещены query и hash; завершающие `/` убираются. Путь очищается от краевых `/`, затем `new URL(`${base}/${path}`)` | клиент 01, 04 |
| Кодирование query-параметров | `url.searchParams.set(name, String(value))` для каждого значения, кроме `undefined`, `null`, `""`; `false` и `0` сохраняются; объект `query` не изменяется | клиент 02, 03; собственная №1 |
| Заголовок `Accept` | `headers: { Accept: "application/json" }`, метод `GET` | клиент 05 |
| Проверка `response.ok` | сразу после получения `Response`; при `!ok` поля берутся из `payload.error`, если тело — JSON, иначе сообщение `HTTP <status>` | клиент 08, 09, 16 |
| Проверка `Content-Type` | только для успешных ответов, после отдельной ветки `204 → null`; должен содержать `application/json` | клиент 07, 10 |
| Разбор JSON | `await response.json()` в `try`; `SyntaxError` сохраняется как `cause` у `invalid-response` | клиент 11 |
| Ограничение времени | `AbortSignal.timeout(timeoutMs)`; `timeoutMs` — положительное целое (по умолчанию 2000, можно переопределить на запрос) | клиент 14, интеграция 12 |
| Внешняя отмена | `AbortSignal.any([signal, timeoutSignal])`; при отказе `fetch` сначала проверяется `signal.aborted` → `aborted`, затем `timeoutSignal.aborted` → `timeout`, иначе `network` | клиент 15, интеграция 13 |

## Доменный модуль задач

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач: `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]`, `meta.total = 12` |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи: `[4, 13, 34]` |
| `getTaskById(25)` | `{ id: 25, title: "Исправить обработку ошибок", completed: true, priority: "high", categoryId: 2 }` |
| `getCategories()` | `1 — Учёба`, `2 — Проект`, `3 — Организация` |
| `loadInitialData({ completed: false, priority: "high" })` | `{ tasks: [4, 13, 34], categories: [3 шт.], meta: { total: 3, filters: {...} } }` |

Правила проверки:

- **фильтры (до запроса, `TypeError`)**: только `completed` (boolean), `priority` (`low`/`medium`/`high`), `categoryId` (положительное безопасное целое), `q` (строка, обрезается `trim`, до 100 символов); `null`, массив и неизвестный ключ отклоняются;
- **задача**: положительный целый `id`, `title` — строка 1–100 после `trim`, `completed` — boolean, допустимый `priority`, положительный целый `categoryId`;
- **категория**: положительный целый `id`, `name` — строка 1–100 после `trim`;
- **коллекция**: `data` — массив, все элементы проходят схему, `id` не повторяются, `meta.total === data.length`;
- любое нарушение схемы ответа → `ApiError` с `kind: "invalid-response"`.

## Последовательная и параллельная загрузка

Два запроса `/debug/delay?ms=300` (временный эксперимент, в рабочий код не включён).

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 605 | 605 | 605 | время ≈ сумма задержек: второй запрос начинается только после ответа на первый |
| `Promise.all` | 302 | 303 | 303 | время ≈ самая долгая задержка: оба запроса отправлены до ожидания, сервер обрабатывает их одновременно |

Ускорение возникает не из-за `Promise.all`, а из-за того, что оба Promise созданы (запросы отправлены) до `await`. `Promise.all` лишь ждёт уже начатые операции и отклоняется при первом отказе. Для зависимых запросов такой приём неприменим.

## Отладка

Значения сняты в Node.js отладочной обёрткой `fetchFn`, переданной в `createApiClient` (она фиксирует аргументы `fetch` и свойства `Response`, после чего возвращает тот же ответ), — это те же точки, что и точки останова «до `fetch`» и «после получения `Response`». Значения `payload` и `ApiError` — результат `requestJson` / `catch`.

| Значение | Успешный запрос `getTaskById(25)` | Ошибочный запрос `getTaskById(999)` |
|---|---|---|
| URL (до `fetch`) | `http://127.0.0.1:5505/api/tasks/25` | `http://127.0.0.1:5505/api/tasks/999` |
| Метод / `Accept` | `GET` / `application/json` | `GET` / `application/json` |
| `response.status` | 200 | 404 |
| `response.ok` | true | false |
| `Content-Type` | `application/json; charset=utf-8` | `application/json; charset=utf-8` |
| Перед `response.json()` | ветка `!ok` пропущена, `status !== 204`, `Content-Type` подходит | `response.json()` вызывается в `readErrorPayload` только для разбора `error` |

## Ответы на контрольные вопросы

1. Promise — объект-обещание будущего результата; значения в нём может ещё не быть, получить его можно только через `await`/`then`.
2. `pending`, `fulfilled`, `rejected`.
3. `fetch` только запускает операцию и сразу возвращает Promise; синхронный код продолжается, ответ обрабатывается позже.
4. Микрозадачи (`then`, продолжение `await`) выполняются сразу после текущего синхронного кода, все подряд; таймер — следующая задача, после всех микрозадач.
5. Всегда Promise.
6. `await` отклонённого Promise выбрасывает его причину как исключение в месте ожидания — его ловит `try/catch`.
7. Сервер ответил — сеть сработала; HTTP-статус ошибки `fetch` не отклоняет.
8. `true` для статусов 200–299.
9. Тело читается из потока асинхронно; `json()` возвращает Promise.
10. Чтобы не разбирать HTML или текст как JSON и сразу получить понятную ошибку `invalid-response`.
11. Структура может не совпадать с контрактом: `data` не массив, неверные типы, повторяющиеся id.
12. Для правильного кодирования query-параметров (пробелы, `&`, `#`, кириллица).
13. `completed=false` — содержательный фильтр; если его выбросить, вернутся все задачи.
14. HTTP-ошибка — ответ получен со статусом вне 2xx; сетевая — ответа нет вообще.
15. Тайм-аут — клиент прервал запрос по истечении времени; отмена — вызывающий код сам вызвал `abort()`.
16. Создаёт `signal`, через который можно прервать `fetch`; `abort()` отклоняет запрос с `AbortError`.
17. Когда запросы независимы — результат одного не нужен для другого.
18. Итоговый Promise сразу отклоняется с этой причиной.
19. Нет, остальные запросы продолжают выполняться.
20. Транспорт (URL, статус, JSON, ошибки) не зависит от предметной области и переиспользуется; `task-api.js` знает только маршруты и схему.
21. Чтобы подменить `fetch` в тестах и проверять клиент без сети.
22. Сборку URL, конфигурацию, обработку 204/HTTP/сетевых/форматных ошибок, тайм-аут, отмену, фильтры, схему и параллельный старт.

25. `api-client.js` (`buildUrl`, `requestJson`, `ApiError`) и функции чтения из `task-api.js`.

## Вывод

Реализованы общий HTTP-клиент (`api-client.js`) и предметный модуль задач (`task-api.js`). Транспорт и предметная область разделены: клиент не знает, что такое задача, поэтому его можно переиспользовать в ПР6. Проходят все три набора проверок: 18 + 26 + 13.

Различия между видами результатов:

- **Ожидание Promise** — запрос ещё выполняется (`pending`), результата пока нет; `await` приостанавливает только текущую `async`-функцию.
- **HTTP-ошибка** (`http`) — сервер ответил, но статусом вне 2xx. `fetch` не отклоняется, поэтому статус проверяется явно; код и детали берутся из конверта `error`.
- **Сетевая ошибка** (`network`) — ответа нет вообще (сервер не запущен, неверный порт), `fetch` отклонён.
- **Неверный ответ сервера** (`invalid-response`) — статус успешный, но не JSON, повреждённый JSON или данные не соответствуют схеме.
- **Тайм-аут** (`timeout`) — ответ не пришёл за отведённое время; запрос прерван клиентом через `AbortSignal.timeout`.
- **Явная отмена** (`aborted`) — вызывающий код сам отменил запрос через `AbortController`; это управляемое действие, а не сбой сервера.
